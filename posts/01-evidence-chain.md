# 一个 LLM 安全漏洞，怎么变成别人能自己跑出来的证据

> 草稿 · 目标平台：知乎 / CSDN / 掘金
> 素材来源：本仓库 `findings.md`「证据链怎么读」一节 + `notes.md` 相关 6 条概念
> 发稿纪律：**只讲方法，不贴具体利用链**

---

## 一、一个几乎所有人都会踩的坑

学安全、做安全研究、或者给团队做安全评审，你大概率写过这样一个东西：

```python
# exploit.py
def test_idor():
    """演示越权：A 读到了 B 的记录"""
    resp = requests.get("/api/records", headers={"Authorization": f"Bearer {token_a}"})
    assert resp.json()["owner"] == "user_b"     # 复现成功
    print("漏洞存在！")
```

然后你改代码，加了个鉴权，写一句"**已修复**"，提个 commit。

在个人笔记里这挺常见。在团队里这很正常。在一个**要写进安全报告**的场景里，这**几乎不可接受** —— 因为三个月后有人问"这个洞真修好了吗"，你能拿出来的只有：

- 一个跑得通的 `exploit.py`（证明漏洞**曾经**存在）
- 一句"已修复"（证明**你想修好了**）

**中间那一步是空的：你没有任何东西能证明修复真的有效。**

---

## 二、问题出在哪：没有红状态的测试证明不了任何修复

这句话值得拆开看。

一份修复有效的证明，本质上要同时成立两件事：

1. 在**修复前**的代码上，它**会失败**
2. 在**修复后**的代码上，它**会通过**

第 2 件事几乎所有人都会做 —— 修完，跑一遍测试，绿了，完事。

**第 1 件事几乎所有人都没做。** 而它才是关键。

考虑一个从来没人验证过它是否有效的测试：

```python
def test_identity_is_from_token():
    assert "body.get(\"user_id\")" not in open("api.py").read()
```

这个断言，绿了。你很开心。

但它证明修复有效吗？**不一定。** 也许代码里写的是 `body.get('user_id')`（单引号）—— 断言照样绿，洞照样在。也许它换成了 `body["user_id"]`。也许它只是把代码挪到了另一个文件里。

**一个从来没红过的测试，可能只是在测一个恒真的东西。** 它绿了，只说明它没测到任何东西。

所以：

> **红→绿是修复有效性的唯一证明。**
> 从没红过的测试证明不了任何修复。

这条听起来像废话，但它是我见过的**最容易被跳过、且跳过之后完全无感知**的一步。跳过的原因通常是"这个测试obviously会红" —— 而这正是最危险的自我说服：它 obvious 到你不会去跑。

## 三、怎么组织证据：tag 对，而不是分支或副本

现在你接受了"要红也要绿"这个要求。接下来是工程问题：

**怎么让这两个状态同时存在、可复现、且不会被后来的改动弄乱？**

我见过三种做法：

### 做法 A：三个分支

```
main          ← 修好的版本
vulnerable/   ← 漏洞版本
fix-verified/ ← "修好了"版本
```

问题：三个分支**会漂移**。你在 `main` 上又修了三个别的洞，`vulnerable/` 早就对不上了 —— 半年后想重放原始攻击，发现靶场已经不是当初那个靶场。

而且三个分支会让人误以为是三个不同的项目。`git log` 里看不出"这是一个项目的三个时间点"。

### 做法 B：三份代码副本（目录或仓库）

问题更重：三倍维护 + 漂移。而且很快没人愿意更新副本里的依赖和配置，最后三份都跑不起来。

### 做法 C（采用）：tag 对 —— 一个项目的三个时间点

```bash
git tag vuln-001   # 指向修复前的代码
git tag fixed-001  # 指向修复后的代码
```

**关键在于：这不是三份代码，是同一份代码的三个时间点。**

于是：

```bash
git checkout vuln-001  && pytest tests/security/test_authz_idor.py   # 红：漏洞真实存在
git checkout fixed-001 && pytest tests/security/test_authz_idor.py   # 绿：修复真的有效
```

**同一条命令，两个结果。**

这份测试文件本身**只写一次**，不存在"红版测试"和"绿版测试"两份拷贝漂移的问题（这是做法 A/B 都会踩的坑）。

而且 tag 有个额外好处：**tag 天然是一个集合**。

```
所有 vuln-XXX tag 的集合 = 随时可 checkout 回来重放攻击的原始靶场
```

你不需要单独维护一个"靶场分支"。攻击面会随着你的学习自然增长 —— 挖到一个新洞就多打一个 tag。

## 四、只有 tag 还不够：证据必须**别人也能跑**

上面这套只在你自己的机器上成立。别人怎么验证？

**答案是：把它接进 CI，并且让 CI 的历史本身成为证据。**

```yaml
# .github/workflows/test.yml
on:
  push:
    branches: [main, develop]
    tags: ['vuln-*', 'fixed-*']      # ← 推 tag 会触发 CI
  pull_request:
    branches: [main, develop]
```

推 `vuln-001` 和 `fixed-001` 这两个 tag，各自触发一次 CI。**Actions 历史里就留下了红和绿两个格子。**

这一步的价值常被低估：

> 证据不应该是"我说我修好了"，也不应该是"截图"。
> 证据应该是**两个可复现的状态** —— 别人能自己跑出来的才算证据，文字描述不算。

CI 的红绿格子是**公开的、持久的、不可篡改的**。这比任何描述都强。

---

## 五、再往前一步：修复必须接成**阻塞**门禁

到这里，你可以证明"这个洞曾经存在"和"我的修复有效"。

**但漏洞可能重开。**

一个真实发生过的场景：

```python
# 半年后，有人加了个新功能
metadata = {**body.get("metadata", {}), "conversation_id": conv_id}
```

他不知道半年后有个洞被修过。他没有恶意，他只是**不知道**。洞重开了，而且没人发现。

**修复没有门禁，等于没修。**

所以修复必须落成 CI 里的**阻塞**步骤：

```yaml
      - name: "Security gate: IDOR / identity (blocking)"
        run: python tests/security/test_authz_idor.py
        continue-on-error: false      # ← 缺了这两字，修复就只是"跑过"
```

`continue-on-error: false` 是关键。默认行为在很多 CI 配置里是"失败也继续"，那样这个步骤就只是**打印一个红色的字**，而不是**挡住这次合并**。

于是：

> **下一个人随手加个 `**metadata`，CI 会当场红给他看** —— 这才叫修复完成。

## 六、两个容易忽略的坑

### 坑 1：取证分支和产品分支，是两件事

新人常见的做法是：直接在产品分支上修，修完 commit 一个"安全修复"。

问题是这样一来，你**永远没有那个红色的状态**。历史被抹平了，证据不存在了。

正确的分工是：

| | 在哪 | 干什么 |
|---|---|---|
| **取证** | `security-lab` 分支 + `vuln-XXX`/`fixed-XXX` tag 对 | 证明"洞真的存在、修的真的有用" |
| **落地** | 产品分支的提交 | 让洞在产品里**真的关上** |

**只做取证不做落地，等于没修**（洞在产品里还开着）。
**只做落地不做取证，等于没法证明**（三个月后没人相信你修好了，因为只有一句"已修复"）。

两件事都要做，且要分开做。

### 坑 2：CI 的可见性本身，是证据链的一部分

这个坑很隐蔽。

我有个仓库的 workflow 配错了一个键（YAML 里同一个 `description` 写了两次，解析器直接拒绝加载整个 workflow）。结果：**每一次 push 都在 Actions 页面留下一个红叉** —— 而且是那种"0 个 job、红在 workflow 加载阶段"的红叉。

一开始我没当回事，直到我发现：**我分不清哪个红叉是"有意的红"（tag `vuln-XXX` 触发的），哪个是"坏了"（CI 自己挂了）。**

一旦分不清，证据链就失效了。因为证据链的全部意义在于"红 = 洞还在，绿 = 洞关了"这个**可读的约定**。当红叉的来源变得随机，这个约定就不成立了。

> **满屏红叉会让人分不清哪个红是「有意的红」、哪个红是「坏了」，证据链直接失效。**

所以：做证据链的人，**同时得是自己 CI 的维护者**。CI 挂了要第一时间修。

## 七、这套方法真正的价值

可能有人会说：这么搞是不是太重了？做个安全项目而已。

我觉得问题的关键是反过来 —— **轻的那套根本不成立**。

一个只有"exploit.py + 已修复"的安全工作，实际交付的是：

- 漏洞存在过 ✅（但只有你电脑上的那份脚本能证明）
- 漏洞修好了 ❌（无证据）
- 漏洞不会重开 ❌（无门禁）
- 别人能验证 ❌（无公开红绿）

**四条里只成立一条。**

而加上 tag 对 + CI 红绿 + 阻塞门禁之后：

- 漏洞存在过 ✅ —— checkout `vuln-001` 就复现
- 漏洞修好了 ✅ —— 同一份测试，`fixed-001` 上是绿的
- 漏洞不会重开 ✅ —— 阻塞门禁挡着
- 别人能验证 ✅ —— Actions 历史里红绿两个格子，谁都能点开看

**四条全部成立。**

这就是我说的"没有红状态的测试证明不了任何修复"的真正重量 —— 它不是一个技术细节，它决定了你的安全工作**是"我觉得"还是"可验证"**。

而最后这一点，在 LLM 安全领域尤其重要。

LLM 安全的很多防御是**内容层**的（"在系统提示里写别听文档的话"）。这类防御有个致命特征：

> **它失败了不会报错。**

代码洞失败了会炸。内容层防御失败了只会让模型偶尔说错话 —— **没有任何信号**。你无法区分"防御生效了"和"这次侥幸没被注入"。

所以在这个领域，能被验证的能力比什么都值钱：

- "我加了一条过滤规则" —— 无法验证，可能没用
- "我加了一条门禁，它在 CI 里挡着" —— **可验证**

**前者是相信，后者是知道。**

## 八、如果你也想搭一套

最小可用版本，四步：

**① 把安全决策抽成零依赖纯函数**

这一步是前提，也是最大的门槛。因为如果你的安全决策写在一个 `import` 起来要 83 秒、还依赖数据库和网络的模块里，那它**根本没法独立测试**，只能靠人肉 review —— 而人肉 review 一定会漏。

抽出纯函数之后，测试就是秒级的。

**② 写测试，先让它红**

```bash
git checkout <修复前的 commit>
python tests/security/test_xxx.py    # 必须 FAIL，exit 1
```

失败信息要**自解释**：

```
✘ 身份不可被请求体覆盖
   最终身份 = 'victim_001'（期望 'attacker_001'）
```

不是 `AssertionError: assert False`。半年后有人读到这条输出，得立刻知道发生了什么。

**③ 修，打 tag 对**

```bash
git tag vuln-XXX    # 红的那一版
git tag fixed-XXX   # 绿的那一版
```

**④ 接进 CI 阻塞门禁，并把 `tags: ['vuln-*', 'fixed-*']` 配上**

推 tag → CI 红绿 → Actions 历史成为公开证据。

---

## 收尾

这套东西的本质，其实和"写单元测试"是同一件事 —— 只是把对象从"函数行为"换成了"**漏洞状态**"。

单元测试测的是"这段代码现在对不对"；
证据链测的是"**这个洞曾经存在，而且确实被关上了，而且关着的时候还会有人守着**"。

从一个工程角度看，这两者都是**把"我相信"变成"我知道"**。

在 LLM 安全这个失败是静默的领域，"我知道"比"我相信"值钱得多。
